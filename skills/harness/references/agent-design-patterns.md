# Codex 多代理設計模式

本文件說明如何把團隊架構模式映射到 Codex 的主代理人與子代理人工作流程。

## 1. 執行模式

### 1-1. 平行子代理人

主代理人同時委派多個彼此獨立的任務，等待所有代理人回傳摘要後再整合。

適合：

- 程式庫探索
- 多來源研究
- 安全、效能、測試等不同面向的審查
- 可按檔案或資料列切分的批次工作

不適合：

- 多個代理人會修改相同檔案
- 下一個任務必須先取得前一個任務的完整結果
- 工作規模太小，協調成本高於收益

### 1-2. 階段式子代理人

主代理人依序啟動代理人；每一階段都要有明確輸出與完成條件。

適合：

- 規格 → 實作 → 測試
- 產出者 → 審查者 → 修正者
- 研究 → 綜整 → 驗證

### 1-3. 混合模式

先以平行代理人蒐集，再由單一角色整合，最後由獨立代理人驗證。這通常是複雜 Harness 最實用的預設模式。

```text
主代理人
├── 探索代理人 A ─┐
├── 探索代理人 B ─┼→ 整合者 → 審查者 → 主代理人完成驗證
└── 探索代理人 C ─┘
```

### 1-4. 單一代理人

若工作無法有效切分，或只有一個小型產物，直接由主代理人完成。Harness 的價值來自清楚的責任與驗證，不來自代理人數量。

## 2. 模式選擇決策

依序回答：

1. 是否真的需要不同角色、上下文、工具或權限？否則使用單一代理人。
2. 工作能否在不共享中間狀態下獨立完成？可以則平行。
3. 工作是否有明確前後相依？有則階段式。
4. 前段可平行、後段需整合與審查？使用混合模式。
5. 是否需要子代理人再委派？只有明確必要時才提高 `agents.max_depth`。

## 3. 六種架構 Pattern

### 3-1. Pipeline

```text
Agent A → Agent B → Agent C → 最終產物
```

適用：每一階段輸出格式固定，且下一階段必須依賴上一階段。

設計重點：

- 每個交接都定義輸入、輸出與驗證條件。
- 上游失敗時停止下游，避免錯誤擴散。
- 大型中間產物寫入 `_workspace/`；小型結果以摘要交接。

### 3-2. Fan-out/Fan-in

```text
              ┌→ Agent A ─┐
主代理人 ─────┼→ Agent B ─┼→ 主代理人整合
              └→ Agent C ─┘
```

適用：多個互不相依的觀點、資料來源、模組或檔案集合。

設計重點：

- 所有代理人的輸出使用相同結構。
- 主代理人等待完整集合，標記缺少或失敗的結果。
- 整合時要解決衝突，不能只拼接摘要。

### 3-3. Expert Pool

```text
領域問題 → [法務、技術、風險、營運] → 綜合判斷
```

適用：同一問題需要不同專業判準。

設計重點：

- 每位專家只處理自己的判斷範圍。
- 先定義共同證據格式與信心等級。
- 若結論衝突，由主代理人依證據與需求做決定。

### 3-4. Producer-Reviewer

```text
Producer → Reviewer → 修正 → 驗證
```

適用：品質比速度重要，且產物可以迭代。

設計重點：

- 審查者採 `sandbox_mode = "read-only"`。
- 審查者回傳具體缺陷、證據、嚴重度與驗收方式。
- 寫入仍由 Producer 或指定實作者負責。
- 預先設定最大迭代次數，避免無限循環。

### 3-5. Supervisor

```text
Supervisor → 判斷任務 → 選擇 Agent → 評估結果 → 下一步
```

適用：工作種類在執行前無法完全預測，或需要依結果動態分派。

設計重點：

- Supervisor 通常就是主代理人，不另外建立只負責轉送的角色。
- 每次分派都要有有界任務與停止條件。
- 保留工作狀態摘要，避免重複分派。

### 3-6. Hierarchical Delegation

```text
主代理人 → 領域主管 → 執行代理人
```

適用：大型計畫同時包含多個相對獨立的子領域，且每個子領域本身仍需分工。

風險：

- 需要提高 `agents.max_depth`。
- 代理人數與 token 成本可能快速增加。
- 中間摘要容易失真。
- 失敗定位與寫入衝突更難處理。

只有上述收益明確高於成本時才使用，並設定最大深度、最大併發與每層回傳格式。

## 4. 選擇代理人類型

Codex 內建代理人包括：

| 類型 | 用途 |
|---|---|
| `default` | 一般用途與未指定角色的後備選擇 |
| `worker` | 實作、修正與執行導向工作 |
| `explorer` | 唯讀探索、程式路徑追蹤與證據蒐集 |

當角色需要固定的責任、權限、工具或工作原則時，在 `.codex/agents/*.toml` 建立自訂代理人。

| 情境 | 建議 |
|---|---|
| 一次性、邊界清楚的探索 | 使用 `explorer` 並給具體任務 |
| 一次性實作 | 使用 `worker`，由主代理人明確限定範圍 |
| 會跨任務重複的專業角色 | 建立自訂代理人 TOML |
| 需要唯讀保證 | 自訂代理人設定 `sandbox_mode = "read-only"` |
| 需要特定 MCP 或技能 | 在自訂代理人設定對應 `mcp_servers` 或 `skills.config` |

未收到明確要求時，不固定 `model` 或 `model_reasoning_effort`；讓代理人繼承父工作階段，避免配置快速過時。

## 5. 自訂代理人結構

位置：`.codex/agents/{agent-name}.toml`

```toml
name = "security_reviewer"
description = "唯讀安全審查者；在變更涉及驗證、權限、輸入處理或敏感資料時使用。"
nickname_candidates = ["Shield", "Sentinel", "Aegis"]
sandbox_mode = "read-only"
developer_instructions = """
## 核心責任
找出可被利用的行為、權限邊界錯誤、資料暴露與缺少的安全測試。

## 輸入
接收變更範圍、需求、相關檔案與既有測試。

## 輸出
依嚴重度列出發現；每項包含證據位置、風險、重現方式與驗收建議。

## 邊界
不要修改檔案。不要把風格偏好當成安全缺陷。

## 失敗處理
若證據不足，明確標記未知資訊與取得方式，不要猜測。
"""
```

必要品質：

- `name` 穩定且唯一。
- `description` 說明何時使用，而不只是角色名稱。
- `developer_instructions` 說明責任、輸入、輸出、邊界、驗證與失敗處理。
- 寫入能力與實際責任一致。
- 不在 TOML 中保存密鑰或帳號資訊。

## 6. 代理人拆分標準

從四個面向判斷：

1. **責任**：能否用一句話說清楚，且不與其他角色重疊？
2. **上下文**：是否需要獨立知識、資料或較乾淨的上下文？
3. **權限與工具**：是否需要不同 sandbox、MCP 或技能？
4. **驗證**：是否有自己可判定的完成條件？

不要拆出：

- 只負責轉貼訊息的代理人
- 沒有獨立輸出的代理人
- 只執行一個簡單命令的代理人
- 與既有角色只有名稱不同的代理人

## 7. 重複使用設計

新增前依序檢查：

1. 既有代理人的 `description` 是否已涵蓋需求。
2. 是否只需補強 `developer_instructions`。
3. 是否應增加一個技能，而不是建立新角色。
4. 是否能以一次性委派完成，不必留下長期配置。

若仍需新增，記錄它與既有角色的邊界差異。

## 8. 區分技能與代理人

| 面向 | 技能 | 自訂代理人 |
|---|---|---|
| 目的 | 可重複的工作方法與知識 | 可委派的專業角色與執行設定 |
| 專案位置 | `.agents/skills/{name}/SKILL.md` | `.codex/agents/{name}.toml` |
| 觸發方式 | Codex 隱式選用或使用者以 `$name` 叫用 | 主代理人依任務委派 |
| 主要內容 | 步驟、判斷、範本、參考資料、腳本 | 責任、邊界、權限、工具、模型設定 |
| 重複使用 | 可供多個代理人使用 | 可載入或停用特定技能 |

同一角色可使用多個技能；同一技能也可供多個角色使用。不要把完整技能全文複製進 `developer_instructions`。
